Порядок має значення: кроки 1–3 роблять сайт юридично придатним приймати
гроші, 4–6 піднімають його, 7 вмикає оплати. Пропустити середину не можна —
кожен наступний крок спирається на попередній.

Чому саме так зроблено — у `CLAUDE.md`. Тут тільки послідовність дій.

## 0. Перед початком: секрети

**Це треба зробити один раз, і краще до деплою.**

`backend/.env` лежить у git разом із `SECRET_KEY`, паролем бази й паролем
адміна. Крім того, `.env.example` колись був побайтовою копією `.env`
із бойовими ключами monobank — і `.gitignore` його явно дозволяє.

```bash
git rm --cached backend/.env
echo "backend/.env" >> .gitignore
git commit -m "прибрати .env з індексу"
```

Після цього **провернути** все, що там лежало: `SECRET_KEY`, пароль
Postgres, пароль адмінки, ключі monobank. Старі значення назавжди
лишаються в історії git — видалення файлу їх не стирає.

## ⚠ Перед підйомом на проді: пароль бази

`docker-compose.yml` більше не хардкодить облікові дані — сервіс `db` бере їх
із `backend/.env`. Але **том із базою на проді вже створений** зі старими
значеннями (`postgres` / `2111` / `prime_platform_db`).

`POSTGRES_PASSWORD` і `POSTGRES_DB` впливають **тільки на перший запуск**
порожнього тому. На вже існуючій базі вони не міняють нічого: пароль
усередині Postgres лишається старим.

Тому в прод-`.env` ці три значення мають **збігатися з тим, що в базі зараз**:

```
POSTGRES_USER=postgres
POSTGRES_PASSWORD=<той, що вже в базі>
POSTGRES_DB=prime_platform_db
DATABASE_URL=postgresql+asyncpg://postgres:<той самий>@db:5432/prime_platform_db
```

Якщо вписати новий пароль, backend упаде з `password authentication failed`,
а виглядатиме це як проблема мережі.

**Щоб справді змінити пароль бази** — спершу підняти старий контейнер і
виконати `ALTER USER postgres WITH PASSWORD '...';`, і лише потім правити `.env`.

## 4а. Робочий простір кабінету (міграції 0011–0012)

Порядок важливий: **бекап → міграції → перезапуск**. Новий код без міграції 0011
не пустить у кабінет (сайт і оплати при цьому працюють).

```bash
sh scripts/backup.sh                                  # див. «Бекапи» нижче
git pull
docker compose build backend nginx
docker compose up -d                                  # створить том uploads_data
docker compose exec backend alembic upgrade head      # 0011, 0012
docker compose restart backend nginx
```

| Міграція | Що робить |
|---|---|
| 0011 | акаунти: роль `owner/admin` замість enum, `name`, `sections`, `must_change_password`, `token_version`, `last_login_at`, місце під 2FA; таблиця спроб входу |
| 0012 | коментарі, оцінки, файли, журнал дій, «прочитано», завдання, нотатки, звіти |

**Що станеться з входом.** Існуючий owner лишається owner-ом з тим самим паролем
(хеші не чіпаються). Старі ролі `MANAGER`/`EDITOR` стають `admin` з усіма розділами.
Імʼя береться з частини пошти до `@`, перейменувати можна в «Команді».
Після оновлення всі мусять увійти заново: стару куку новий код не приймає.

**`ADMIN_EMAIL` / `ADMIN_PASSWORD` у `.env` більше не читаються**, автостворення
owner-а при старті прибрано. Рядки в `.env` нічого не ламають, але їх можна видалити.
Новий owner або відновлення доступу, якщо owner забув пароль:

```bash
docker compose exec backend python -m app.cli create-admin   # пароль вводиться інтерактивно
```

Якщо пошта вже є — акаунт стає owner-ом і отримує новий пароль, старі сесії закриваються.

**nginx.** У `nginx.conf` додано `client_max_body_size 25m` і окремий
`location = /api/admin/files` до 310 МБ (відео). Без цього файли понад 1 МБ
отримували б 413. Перевірити конфіг до перезапуску:

```bash
docker compose exec nginx nginx -t
```

**Налаштування (необовʼязково, є значення за замовчуванням)** — у `backend/.env`:
`UPLOAD_MAX_MB=20`, `UPLOAD_VIDEO_MAX_MB=300`, `SESSION_HOURS=12`,
`LOGIN_MAX_FAILURES=5`, `LOGIN_WINDOW_MINUTES=15`. Якщо міняєте ліміт відео,
змініть і `client_max_body_size` у `location = /api/admin/files`.

Перевірка після підйому: увійти власником → «Команда» → видно вільне місце
на диску → створити тестовий акаунт → увійти ним з тимчасовим паролем →
система вимагає змінити пароль.

## Бекапи

До 15.11.2026 бекапів не було взагалі. `scripts/backup.sh` робить три файли
в `/var/backups/prime` (змінна `BACKUP_DIR`):

- `prime-db-ДАТА.dump` — `pg_dump -Fc` бази;
- `prime-uploads-ДАТА.tar.gz` — том файлів кабінету;
- `prime-certificates-ДАТА.tar.gz` — PDF сертифікатів.

Копії старші за 14 днів (`KEEP_DAYS`) видаляються. Паролів у скрипті немає:
дамп робиться всередині контейнера `db` з його ж змінних.

**Cron** (щодня о 03:30, на сервері):

```bash
crontab -e
30 3 * * * cd /шлях/до/english_app_info && sh scripts/backup.sh >> /var/log/prime-backup.log 2>&1
```

Перший раз запустити руками й переконатися, що в теці три непорожні файли.

**Відновлення:**

```bash
# база (УВАГА: перезаписує поточну)
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < prime-db-ДАТА.dump
# файли кабінету
docker compose exec -T backend tar -C /data -xzf - < prime-uploads-ДАТА.tar.gz
# сертифікати
tar -xzf prime-certificates-ДАТА.tar.gz
```

**Копія поза сервером — обовʼязково.** Бекап на тому самому диску не рятує,
якщо зник сервер чи диск. Найпростіше — `rclone` у будь-яке хмарне сховище:

```bash
apt install rclone
rclone config                       # створити remote, напр. "gdrive" (Google Drive) або S3/Backblaze B2
# у cron перед командою:
30 3 * * * cd /шлях/до/english_app_info && BACKUP_REMOTE=gdrive:prime-backups sh scripts/backup.sh >> /var/log/prime-backup.log 2>&1
```

Скрипт копіює туди свіжі файли за останню добу. У самому сховищі налаштуйте
зберігання ~30 днів. Раз на місяць варто відновити дамп у dev і переконатися,
що він читається: неперевірений бекап — це надія, а не бекап.

| Міграція | Що робить |
|---|---|
| 0013 | `leads`, `orders`: UTM, fbclid, referrer, landing_page, перший/останній дотик, fbp/fbc, згода на Meta; `leads.level`, `leads.event_id` (унікальний); статуси заявок «пробний призначено», «був на пробному» |

Старі заявки й замовлення лишаються з порожнім джерелом. Відкат `alembic downgrade 0012_workspace`
повертає заявки з новими статусами в «на зв'язку».

### Змінні оточення (`backend/.env` на сервері, у git їх немає)

| Змінна | Звідки | Що буде, якщо порожня |
|---|---|---|
| `META_PIXEL_ID` | Events Manager → ваш Pixel → Налаштування | Pixel на сайті не вантажиться |
| `META_CAPI_TOKEN` | там само → Conversions API → «Згенерувати токен доступу» | сервер нічого не шле в Meta |
| `META_TEST_EVENT_CODE` | Events Manager → «Тестові події» | події йдуть у бойовий потік |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `LEAD_NOTIFY_EMAIL` | поштовий сервіс (для Gmail — «пароль додатка») | листів про заявки немає, заявки видно в кабінеті |

Після зміни `.env`: `docker compose up -d backend` (контейнер перечитує `env_file`).
Перевірити, що конфіг їх бачить, не друкуючи значень:

```bash
docker compose exec backend python -c "from app.core.config import settings as s; print(bool(s.meta_pixel_id), bool(s.meta_capi_token), bool(s.meta_test_event_code), bool(s.smtp_host))"
```

### Перевірка в Events Manager (перед стартом реклами)

1. Задати `META_TEST_EVENT_CODE`, перезапустити backend.
2. Відкрити сайт у звичайному вікні, натиснути «Прийняти все» в банері cookie.
3. Events Manager → «Тестові події»: має зʼявитись `PageView` (браузер).
4. Залишити заявку на `/trial` → `Lead` двічі (браузер і сервер) з однаковим event ID,
   Meta показує їх як одну подію («Deduplicated»).
5. На `/checkout` натиснути «Оплатити» → `InitiateCheckout`, теж із дедуплікацією.
6. `Purchase` іде ЛИШЕ з сервера після підтвердженої оплати (банк або «Оплата вручну»
   в кабінеті). Із браузера його немає навмисно.
7. **Прибрати `META_TEST_EVENT_CODE`** і перезапустити backend: інакше бойові події
   так і лишаться в тестовій вкладці.

Без згоди на cookie («Лише необхідні») у Meta не йде нічого: ні з браузера, ні з сервера.

## Автооновлення сертифіката Let's Encrypt

**Нічого міняти на сервері не треба:** усе вже в `docker-compose.yml`. Тут опис, як це
працює і як перевірити.

**Сервіс `certbot`** — цикл `certbot renew` кожні 12 годин. Сертифікат перевипускається,
лише коли до кінця лишається менше 30 днів; інакше прогін порожній.
`--deploy-hook` пише в лог рядок `[certbot] сертифікат оновлено …` лише при справжньому
перевипуску.

**`--quiet` тут свідомо НЕ стоїть** (див. CLAUDE.md, «Сертифікат прострочувався у вересні 2026»):
з ним помилки продовження теж зникають із логів, і про проблему дізнаються, коли сертифікат
уже прострочений. Якщо логи certbot заважають, краще зменшити `max-size`, ніж ховати помилки.
Якщо все ж потрібен `--quiet`, додати його в рядок `certbot renew` у `docker-compose.yml`.

**Reload nginx — у контейнері `nginx`, не в certbot.** nginx тримає сертифікат у памʼяті,
тому після перевипуску файлу його треба перечитати. У `command` контейнера `nginx` фоновий
цикл `nginx -s reload` кожні 6 годин; reload не рве відкриті зʼєднання. Тож новий
сертифікат починає віддаватись не пізніше ніж через 6 годин після перевипуску.
Доступ certbot до `docker.sock`, щоб він сам робив reload, не даємо: це фактично root на хості.

**Перевірка:**

```bash
docker compose logs --tail 50 certbot                      # є прогони, немає помилок
docker compose exec certbot certbot certificates            # дата закінчення
echo | openssl s_client -connect my-prime-academy.com:443 -servername my-prime-academy.com 2>/dev/null \
  | openssl x509 -noout -enddate                            # що реально віддає nginx
docker compose exec certbot certbot renew --dry-run --webroot -w /var/www/certbot   # тест без перевипуску
```

Якщо дати в `certbot certificates` і `openssl` різні — nginx ще не перечитав сертифікат:
`docker compose exec nginx nginx -s reload`.

## 7. Оплати — вмикати ОСТАННІМИ

Спочатку пісочниця, наскрізь:

```
https://u2-demo-ext.mono.st4g3.com
store: test_store_with_confirm
key:   secret_98765432--123-123
```

Прогнати повний сценарій: створення замовлення → ПЧ → колбек →
`GET /api/orders/{id}/state` → підтвердження. Окремо перевірити
`CLIENT_NOT_FOUND`: людина має **мовчки** потрапити на картковий платіж,
без повідомлення про помилку.

І лише потім у конфізі:

```python
payments_enabled = True
```

Вимикач саме в конфізі, щоб вимкнути оплати без релізу, якщо щось піде не так.

## Що лишається відкритим

- **Питання до підтримки monobank:** таблиця комісій за кількістю частин
  (публічно тільки «від 2,9%») і чи можливе часткове повернення.
- **Версії в `requirements.txt` не зафіксовані** — через це вже ламався
  bcrypt при пересборці. Варто перейти на lock-файл.
- **Відгуки й галерея викладачів** — повернути, коли буде 5–8 реальних
  відгуків і 4+ живих профілі. Вигаданих не додавати: це заборонена
  оманлива практика й порушення правил Google Ads і Meta.
- **Сертифікат Let's Encrypt** — автопродовження й reload nginx уже
  налаштовані, найближче продовження близько 23 грудня 2026.
  Після цієї дати варто разово перевірити логи certbot.
